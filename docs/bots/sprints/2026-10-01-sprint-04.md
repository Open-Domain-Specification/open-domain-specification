1. The open issue count grew because new review counterexamples became tickets while no model fixes landed.
2. Reviewers found adjacent defects because the validator's timing reach was patched path by path rather than specified over guard count, lifecycle stage, local call depth and independent route coverage together.
3. The local gate stayed green because the regressions covered the reported path, not the semantic matrix; the gate can only check cases written down.

5. That loop persisted because there was no WIP limit or integration checkpoint. The owner called this out after 16 issues were created on 2026-10-01 while 25 cards remained `doing` and 54 GitHub issues were open.

Correction: no new reviewer request or separate issue for adjacent #131 cases while the local matrix is incomplete. Delegate bounded audits. ### Retrospective checkpoint after the local clean-code audit

The delegated audit found that route intersection still omitted independent named guards and public direct entry, while process `on` events were assumed to precede every command. It also found factorial caller-path enumeration, a valid policy answer trigger missing from held facts, and reader prose that overstated process timing. These are local findings before final reviewer use; no new issue or GitHub CI run resulted. Five whys: the implementation enumerated apparent paths; its route list omitted direct and named-guard entries; it treated process subscriptions as ordered; the tests exercised only the paths already implemented; and the audit plan had no explicit distinction between eventual reaction reach and facts guaranteed at precondition time. The corrective action is one bounded fixed-point must-fact analysis plus direct/round-trip negative and positive twins for named guards, direct calls, policy answers and process starts. The lead owns the action; the tester and production owner verify it before the next checkpoint. No final reviewer is called on this working tree.

The reference-model rebuild then exposed a Petstore approval rule that had never linked its check to approval: the process issued both operations independently. Why did a new diagnostic appear? The stricter reach rule stopped lending one command's fetched summary to another. Why could it lend before? The old checker unioned named guards and process subscriptions. Why did the reference model permit it? Its diagram and prose implied a check-before-approve order without a local call edge. Why was the gap missed? The pinned zero-diagnostic result tested the prior checker, not the causal route the source described. Why did it persist? There was no source-to-call-chain assertion for that business rule. The model owner changed the Petstore front to fetch and then call approval, removed the process's bypass, added that assertion and regenerated the model. Its pinned zero-diagnostic list was not edited. The next checkpoint is the full gate on a clean committed candidate.
