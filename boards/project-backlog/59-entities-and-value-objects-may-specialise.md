- **ironhide-deep** (2026-09-05T14:45:00.000Z): **The reference models are not the accounts.** The card asks for "NorthBank's account kinds at least", and decision 22's context reads NorthBank's accounts as current, savings and loan accounts. NorthBank's DISCOVERY.md does not: the Accounts Team lead says "on our platform that means current accounts; savings are still Sovereign rows and will be the same shape when they come across", and loans are Lending's own aggregate in another bounded context. Kinds of Account would have been invented, which the brief forbids, so I took the account kinds the interview does state — the Core Banking lead's "a ledger account is a customer's account number or a nominal: the loan book, scheme suspense, fee income". `LedgerAccount` was one value object with `kind: 'customer' | 'nominal'` and two attributes described "set when kind is customer" and "set when kind is nominal": exactly the shape decision 22 exists to replace. It now has two kinds, `CustomerLedgerAccount` (the account number) and `NominalLedgerAccount` (the nominal code), and its own description says no posting ever lands on a plain LedgerAccount, which is where decision 22 puts abstractness. The second model is StreamLine, whose Catalogue interview opens "a title is a film or a series": `Film` (holding `playableRenditionSet`) and `Series` (which `includes` Season at `1..*`) are now kinds of `Title`, and the `kind` attribute and the `*` on `has-seasons` are gone. Both models' DISCOVERY.md carry a revision section saying what changed and why, and NorthBank's says plainly why the accounts were left alone and when to revisit. If the lead wants Account specialised anyway, that is a change to what the interview says, and belongs on a card that changes the interview.
- **ironhide-deep** (2026-09-05T14:45:00.000Z): **Two judgement calls inside `cross-aggregate-reference` and `aggregate-tree`, both mine, both reversible in a line.** First: a cross-aggregate `references` may now target a kind of the other aggregate's root, not only the root itself (`reachedAsRoot` in `packages/core/src/validate.ts`). Decision 22 says a kind of the root is reached through it, and an instance of the kind *is* an instance of the root carrying the same identity, so refusing the reference would force a modeller to name Account where the business names LoanAccount and lose the fact. The relaxation is narrow: a kind of a non-root entity is still refused, because it does not specialise the root. Second, and more consequential: `orphanEntities` now treats a kind as reached wherever its parent is. Without that, every kind of a root is a `aggregate-tree` warning ("nothing inside the boundary can get to it") the moment it is declared, and StreamLine would have produced four of them. I read the card's "`aggregate-tree` unchanged" as being about containment — the `includes` cycle walk, which specialisation is deliberately not an edge of, and the includes/uses target checks, which read declared relations only — rather than about reachability, where decision 22's own words ("a kind of the root is reached through it") settle it. Say the word if you read it the other way.
- **ironhide-deep** (2026-09-05T14:45:00.000Z): **What "inherited relations and attributes are the subtype's" changed, rule by rule.** `attribute-relation-coherence` reads effective attributes and effective relations, so a kind that adds an attribute typed by a value object its parent already `uses` is coherent, and so is a kind that uses one the parent's attribute names; it still reports only what the member declares itself, so a parent's own mismatch is one diagnostic on the parent rather than one per kind of it. `entity-identity` reads effective attributes, so a kind is identified by whatever it is a kind of and does not warn — the alternative would have been every kind restating the parent's id, which `specialisation-redeclares` then refuses. `cross-aggregate-reference` needed nothing on the source side and the code comment says why: `specialisation-in-boundary` keeps an entity's parent in the same aggregate, so an inherited relation crosses exactly what the parent's crosses and is reported once, where it is declared; only the target side moved. `cross-context-relation` deliberately reads *declared* relations only: a value object may be a kind of one borrowed over a shared kernel, and reading its inherited relations as its own would make every such kind an error and the borrowing useless.
- **ironhide-deep** (2026-09-05T14:45:00.000Z): **Where the generalisation is drawn, and what it does not draw.** Core collects the subtypes in scope on `ODSRelationGraph` (`subtypes`) and `ODSRelationMap` adds one `specialises` edge per kind, from the kind to what it is a kind of, with no label and no cardinality — the line says the whole of it. Graphviz draws `arrowhead: "onormal"` solid; PlantUML `--|>`; Svelte Flow a new `marker-hollow` triangle at the target, filled with `--bg` so the background shows through, registered as `relation-specialises` and given a legend row ("hollow triangle — Generalisation (is a kind of)") and a story. What none of the three do is redraw a parent's associations on the kind: in UML you follow the generalisation, and the kind's class box carries its own attribute compartment. The pages follow the same rule — the entity page's Relations tables list declared relations, and the header's "A kind of" is the link a reader follows for the rest. Only the attribute table inherits, because the card asked for it and because an attribute list with a hole in it is a different claim about what the thing holds. If you want the relations table to grow an inherited group too, it is the same `DataTable` groups mechanism and about ten lines; it was not on the checklist so I left it.
